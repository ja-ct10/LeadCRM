Suggested Migration Order

Sequence that avoids FK dependency conflicts:

  1. Organization — independent, but Contact and Deal depend on it
  2. RoleDefinition — independent, can run in parallel
  3. Task — depends on Deal (already in DB)
  4. Template — independent
  5. Activity — polymorphic, after all target entities exist
  6. WorkflowTriggerRecord → WorkflowExecutionRun → WorkflowExecutionStep — sequential chain
  7. Invoice — depends on Deal + Contact
  8. ServiceOrder — depends on User
  9. Asset / InventoryItem — last (low priority)

Schema Recommendations

10 structural improvements based on SaaS scalability patterns, RBAC best practices, and audit requirements. Prioritized by production impact.

HIGH PRIORITY
🔴 Add composite indexes on tenantId + query fields
Why: Every query filters by tenantId. Without indexes, PostgreSQL scans the entire table. At scale (10k+ tenants, 1M+ rows) queries go from 50ms → 5,000ms. Critical for Contact, Deal, AuditLog.
@@index([tenantId, createdAt]) @@index([tenantId, status]) @@index([tenantId, email]) @@index([tenantId, assignedUserId])
HIGH PRIORITY
🔴 User.role String → UserRole junction table
Why: Current design prevents dynamic role creation, multi-role assignment, and granular permission changes without touching every User row. Client Admins can't create custom roles.

Fix: User ←→ UserRole ←→ RoleDefinition
model UserRole { id String @id @default(cuid()) userId String roleId String tenantId String user User @relation(...) role RoleDefinition @relation(...) @@unique([userId, roleId]) }
HIGH PRIORITY
🔴 Add soft delete (deletedAt / deletedBy) alongside isArchived
Why: isArchived mixes user-initiated hiding (reversible) with GDPR deletion (permanent). Without deletedAt, you can't comply with "right to be forgotten" requests or track who deleted what.
isArchived Boolean @default(false) archiveReason String? deletedAt DateTime? // GDPR hard delete deletedBy String? // FK→User
MEDIUM PRIORITY
🟡 Deal.contactIds JSON array → ContactDeal junction table
Why: JSON arrays break FK constraints (no data integrity), can't be JOINed efficiently, and can't store relationship metadata (who added this contact? when? what role?).
model ContactDeal { id String @id @default(cuid()) contactId String dealId String tenantId String role String? // "Primary" | "Decision Maker" addedBy String? // FK→User addedAt DateTime @default(now()) @@unique([contactId, dealId]) }
MEDIUM PRIORITY
🟡 Add Contact.ownerId separate from assignedUserId
Why: assignedUserId = who's handling the lead now (changes). ownerId = who originally captured it (immutable). Without this, you can't track commission attribution when leads are reassigned between reps.
assignedUserId String? // current handler ownerId String // original capturer (immutable) ownershipHistory JSON? // [{assignedTo, assignedBy, reason}]
MEDIUM PRIORITY
🟡 Tenant.subscriptionStatus separate from Tenant.status
Why: status = System Admin approval state. subscriptionStatus = PayMongo billing state. A tenant can be ACTIVE (approved) but PAST_DUE (payment failed). Conflating these blocks accurate PayMongo webhook handling.
status TenantStatus // SANDBOX|ACTIVE|SUSPENDED subscriptionStatus SubscriptionStatus // TRIAL|ACTIVE|PAST_DUE|CANCELLED trialEndsAt DateTime? subscriptionEndsAt DateTime?
MEDIUM PRIORITY
🟡 Add AuditLog.ipAddress + userAgent for security forensics
Why: Security incidents (unauthorized access, account takeover) require IP + User-Agent context to investigate. ~50 bytes per log. GDPR requires tracking who accessed data from where.
ipAddress String? // req.ip userAgent String? // req.headers['user-agent'] sessionId String? // trace session context
LOW PRIORITY
🔵 Add Deal.closedAt timestamp
Why: updatedAt changes on every field edit. closedAt captures the exact moment a deal hit "Closed Won/Lost" — critical for sales velocity metrics (average time-to-close).
closedAt DateTime? // set when stage → Closed Won/Lost
LOW PRIORITY
🔵 Add Campaign.scheduledFor for future scheduling
Why: Currently no way to schedule a campaign in advance. Add scheduledFor + cron job checking status=SCHEDULED AND scheduledFor <= now().
scheduledFor DateTime? // null = send immediately sentAt DateTime? // actual send timestamp
LOW PRIORITY
🔵 Add Stage.color for UI pipeline customization
Why: Stage colors are currently hardcoded in the frontend. Storing them in DB lets Client Admins customize pipeline colors per tenant without a deployment.
color String? // hex e.g. "#6366f1"

Lead → Deal → Invoice Flow

Complete lifecycle from lead capture to payment. Shows which entities are created, updated, and triggered at each step.

1
Lead Capture
Sales Rep creates Contact via ContactsPage or campaign response.
Default status = WARM · score = 75
Required: contactPerson, companyName, email OR phone
Contact (created)AuditLog: contact.createdActivity: contact-created
2
Lead Qualification
Sales Rep engages contact. Promotes status to HOT (score=95).
Workflow engine evaluates contact.status_changed → HOT trigger.
May auto-fire: "Send Welcome Email", "Create Follow-up Task".
Contact (status=HOT)Workflow triggeredTask (auto-created)
3
Deal Creation
Sales Rep opens Pipeline → "Add New Deal".
Links to Contact, selects Pipeline (Sales Inquiries), Stage (Discovery), sets value + priority + expected close date.
Deal.history initialized with first entry: {stageId, timestamp, userId}
Deal (created)Pipeline / StageAuditLog: deal.created
4
Stage Progression
Sales Rep drags deal card: Discovery → Assessment → Proposal → Negotiation.
Each move appends to Deal.history[]: {stageId, previousStageId, timestamp, userId}
Workflow engine evaluates deal.stage_changed on every move.
Example: "Proposal" stage → auto-create Task "Prepare Proposal Document".
Deal.stageId updatedDeal.history[] appendedWorkflowExecutionRunTask (auto-created)
5A
Deal Won ✓
Deal moved to Closed Won.
Contact.status → CLOSED.
Deal.closedAt stamped (recommended).
Sales Rep clicks "Convert to Invoice" → Invoice created linked to Deal.
Deal (stageId=ClosedWon)Contact (status=CLOSED)Invoice (created)
5B
Deal Lost ✗
Deal moved to Closed Lost.
Lost Reason modal required → Deal.lostReason stored.
Contact.status → COLD or CANCELLED.
Visible in History tab and Deal Details Modal.
Deal.lostReasonContact (status=COLD)AuditLog
